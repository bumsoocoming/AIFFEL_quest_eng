## 1. 실습 개요

Day 2의 친절한 서버를, **여러 명이 동시에 불러도 죽지 않는 서버**로 개선했습니다.
핵심: 기다림은 겹치고, 무거운 추론은 옆방(스레드풀)으로 떼어내고, 예외는 한곳에서 잡고, 모든 일은 로그로 남긴다.

## 2. 실험 결과 요약

### §3 문제 재현 — 함정 vs 옆방

| 버전 | 동시 3요청 | 추론 중 헬스체크 |
|------|-----------|-----------------|
| **함정 (async + blocking)** | 3·6·9초 (순차) ❌ | **2.50초** (맥박 멈춤) ❌ |
| **옆방 (일반 def)** | 셋 다 3.01초 ✅ | **0.00초** (즉시) ✅ |
| **전용 풀 (run_in_executor)** | 셋 다 3.01초 ✅ | **0.00초** ✅ |

→ 같은 추론인데 **어디서 돌리느냐**가 운명을 갈랐습니다.

### §6 최종 서버 검증 (실제 MNIST)

```
STEP 1 헬스체크    : 200, model_loaded=True
STEP 2 단일 추론   : 정답 7 → 예측 7 (confidence 1.0)
STEP 3 동시 확대   : 1개 0.01초 / 2개 0.02초 / 4개 0.03초 / 8개 0.05초
STEP 4 추론 중 맥박 : /health 0.004초 (즉시)
STEP 5 비정상 입력 : 422 + 로그 WARNING, 직후 정상 200 (서버 생존)
```

→ 요청이 8배 늘어도 시간은 거의 안 늘어남 = **비동기 동시성 입증**.

## 3. 체크포인트 답변

### ✅ §1 체크포인트

**Q1. 추론 3초짜리 서버에 3명이 동시에 오면 마지막 사람이 9초 걸리는 이유는?**

FastAPI의 이벤트 루프(일꾼)가 사실상 한 명이기 때문입니다. `async def` 안에서 무거운 계산이 루프를 붙들면, 앞 요청이 끝나야 다음 요청을 시작할 수 있습니다. 그래서 A는 3초, B는 6초, C는 9초로 순차 처리됩니다. (서버가 느려서가 아니라 구조의 문제)

**Q2. I/O-bound와 CPU-bound의 차이는? 모델 추론은 어느 쪽입니까?**

- **I/O-bound**: DB·외부 API·파일처럼 시간 대부분을 **응답을 기다리며** 보냄. 비동기 효과가 큼.
- **CPU-bound**: 계산을 쉬지 않고 함. 기다리는 틈이 없어 비동기 효과가 없음.
- **모델 추론은 CPU-bound**입니다. 그래서 `async`만 붙여서는 빨라지지 않고, 오히려 루프를 붙들어 위험합니다.

**Q3. 이벤트 루프가 '한 명'인데도 여러 요청을 빠르게 처리하는 비결은?**

한 작업이 '기다림(I/O)'에 들어가는 틈에 잽싸게 다음 작업으로 갈아타기 때문입니다. 기다리는 시간을 버리지 않고 다른 일을 채워 넣어, 한 명으로도 여럿을 동시에 상대합니다.

**Q4. `async def` 안에서 무거운 추론을 직접 돌리면 왜 위험합니까?**

추론이 이벤트 루프 '위'에서 직접 돌아 루프를 붙들기 때문입니다. 그동안 새 요청은 물론 `/health` 헬스체크까지 전부 대기합니다. 로드밸런서가 무응답을 "죽었다"고 판단해 멀쩡한 서버를 트래픽에서 빼버릴 수 있습니다.

### ✅ §4 체크포인트

**Q1. 스레드풀이란 무엇이며, 왜 '미리 정해진 수'로 만듭니까?**

스레드풀은 일손(스레드)을 미리 N명 모아둔 대기조입니다. 요청마다 스레드를 새로 만들면 생성 비용이 크기 때문에, 처음에 N명을 만들어 두고 재활용합니다. 이 N이 '풀 크기'입니다.

**Q2. `run_in_executor`는 무슨 일을 합니까? `await`의 역할은?**

`run_in_executor`는 "이 함수를 옆방(스레드풀)에서 돌리고, 끝나면 결과를 받아와"라는 의미입니다. 무거운 추론을 옆방에 던진 뒤 `await`가 **이벤트 루프를 풀어줘서**, 그 시간 동안 루프는 새 요청·헬스체크를 처리합니다. 추론이 끝나면 `await`가 결과를 회수합니다.

**Q3. CPU 추론과 GPU 추론의 권장 풀 크기는 각각 얼마입니까?**

- **CPU 추론**: ≈ 코어 수 (`os.cpu_count()`). 코어보다 일손이 많으면 손 바꿔쥐는 낭비로 오히려 느려집니다. (이 PC는 12코어)
- **GPU 추론**: 1~2. GPU 자체가 거대한 병렬 계산기라, 일손을 늘려도 GPU 앞에 줄만 길어지고 메모리 부족 위험만 커집니다.

**Q4. 일반 def도 동작하는데 굳이 전용 풀을 쓰는 이유 두 가지는?**

① **크기를 직접 결정**할 수 있습니다. 기본 풀(40)은 프레임워크 소관이라 GPU용으로 1~2로 줄일 수 없지만, 전용 풀은 하드웨어에 맞춰 정할 수 있습니다.
② **추론 부하를 격리**합니다. 기본 풀은 모든 `def`가 공유해서 추론이 점령하면 다른 작업까지 밀리지만, 전용 풀은 추론만 써서 다른 기능에 영향이 없습니다.

### ✅ §5 체크포인트

**Q1. 입력 검증(Day 2)을 통과한 요청도 서버를 터뜨릴 수 있는 예를 드세요.**

모델 파일 손상으로 추론이 깨지는 경우, GPU 메모리가 바닥나는 경우, 멀쩡해 보이던 이미지가 디코딩에서 깨지는 경우 등입니다. 이들은 모두 입력 검증을 통과한 뒤, 서버 내부에서 발생합니다.

**Q2. 핸들러마다 try/except를 다는 대신 전역 핸들러를 쓰는 이유는?**

엔드포인트가 10개면 try/except를 10번 반복해야 하고, 새 엔드포인트에서 한 번이라도 빠뜨리면 거기서 사고가 납니다. 대신 맨 아래에 **그물 하나(전역 핸들러)**를 치면, 어디서 난 오류든 못 잡은 것은 전부 그곳으로 모입니다. 반복도 없고 누락도 없습니다.

**Q3. `print` 대신 `logging`을 쓰면 좋은 점 세 가지는?**

① **시각·모듈명 자동**: `2026-06-11 12:50 ERROR [ml_api] ...`처럼 언제·어디서인지 자동으로 붙습니다.
② **심각도 단계 구분**: INFO→WARNING→ERROR→CRITICAL로 나뉘어 "WARNING 이상만 보기"가 한 줄 설정입니다.
③ **어디로든 전송**: 설정만 바꾸면 화면·파일·외부 모니터링으로 같은 기록을 보낼 수 있습니다.

**Q4. 미들웨어가 '톨게이트'에 비유되는 이유는?**

모든 요청·응답이 반드시 지나는 단 하나의 길목이기 때문입니다. 톨게이트처럼 들어올 때 시계를 켜고, 나갈 때 `POST /predict -> 200 (0.045s)` 한 줄을 남깁니다. 한 번만 등록하면 이후 모든 엔드포인트에 자동 적용됩니다.
